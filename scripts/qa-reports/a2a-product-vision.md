# A2A Network: Product Vision

> Документ для дизайнера и инженера. Версия 1.0, 2026-03-29.

---

## 1. Product Vision Statement

**AI-агенты в Neva Messenger — это невидимые социальные координаторы.** Они не спрашивают пользователя "что ты хочешь?", а сами замечают потребности из переписок, координируют между собой, уважают границы каждого и подсказывают момент, когда стоит действовать.

**Value proposition (1 предложение):**
Neva A2A превращает мессенджер из инструмента "я пишу — ты отвечаешь" в живую социальную сеть, где агенты друзей тихо договариваются между собой, экономя десятки сообщений и неловких пауз.

## 2. Переосмысление "Кто свободен?"

### 2.1. Проблемы текущей реализации

1. **Нет UI результатов.** Пользователь нажимает кнопку, запрос уходит — и ничего не видит. Результаты стримятся через WebSocket (`agent_dialog_update` с `partialResult`), но на клиенте нет компонента для агрегированного отображения.
2. **Слишком утилитарно.** "Кто свободен?" — это broadcast без социального контекста. Нет разницы между "пойти в бар" и "помочь с переездом".
3. **Спам-потенциал.** Каждый друг получает запрос, даже если он неуместен в контексте (например, рабочий коллега в 2 часа ночи).
4. **Нет follow-up.** После ответов нет следующего шага: нет координации "а куда идём?", "во сколько?", "кого ещё зовём?".

### 2.2. Новая концепция: "Давай соберёмся"

Вместо сухого "кто свободен?" — полноценный сценарий социальной координации с тремя фазами:

#### Фаза 1: Намерение (Intent)
Пользователь описывает что хочет **естественным языком**:
- "Хочу в бар вечером, человека 3-4"
- "Нужна помощь с переездом в субботу"
- "Кто-нибудь на покер в пятницу?"
- "Хочу поужинать с кем-то, грустно одному"

Система парсит:
- **Тип активности:** досуг / помощь / поддержка / работа
- **Время:** сегодня вечером / конкретная дата / "когда-нибудь"
- **Размер группы:** 1 человек / 3-4 / большая компания / не важно
- **Настроение запроса:** веселье / нужна помощь / одиноко / деловое

#### Фаза 2: Умный отбор (Smart Targeting)
Агент НЕ рассылает всем подряд. Он выбирает подмножество друзей на основе:

| Фактор | Источник данных | Пример |
|---|---|---|
| Релевантность интересам | `contact_intelligence.persona.activeTopics` | Покер → только тем, кто играет |
| Настроение друга | `contact_intelligence.moodHistory` | Если друг stressed → не звать на тусовку, но звать "поддержать" |
| Социальный контекст | `contact_memory` + `relationshipType` | "Ужин" → close friends, не work |
| Время суток / часовой пояс | Метаданные сообщений | Не тревожить в 2 ночи |
| История отказов | `agent_dialogs` с `status: denied` | Если Коля 3 раза отказал от баров → не звать |
| Свежесть общения | Последнее сообщение | Давно не общались → может стоит позвать |

**AI-обогащение подсказок:**
- "Маша сейчас грустит — может обрадуется приглашению" (mood declining → suggestion)
- "Вы с Петей не общались 2 недели — хороший повод" (silence trigger)
- "Коля вчера писал что устал — может не сегодня" (mood: stressed)

#### Фаза 3: Результаты + Координация
**Экран результатов** (заменяет текущий пустой UI):

```
┌──────────────────────────────────────┐
│ Давай соберёмся                      │
│ "В бар вечером, 3-4 человека"        │
│                                      │
│ ✅ Маша — Свободна! "Ура, давно      │
│    хотела"                           │
│    [Агент автоматически]             │
│                                      │
│ ✅ Петя — Свободен "Только после 8"  │
│    [Ответил сам]                     │
│                                      │
│ ⏳ Коля — Ждём ответа...             │
│                                      │
│ ❌ Аня — Занята "Дедлайн на работе"  │
│    [Агент автоматически]             │
│                                      │
│ 💡 Агент: "Маша и Петя свободны.     │
│    Может в Bar 23 на Рубинштейна?    │
│    Маша была там на прошлой неделе"  │
│                                      │
│ [Создать группу]  [Написать всем]    │
└──────────────────────────────────────┘
```

**Ключевые элементы:**
1. **Карточки ответов** стримятся в реальном времени (уже есть WebSocket `partialResult`)
2. **Метка автономии** — видно, ответил человек сам или его агент (прозрачность)
3. **AI-саммари** внизу — агент подводит итог и предлагает следующий шаг
4. **Кнопка "Создать группу"** — из ответивших положительно автоматически создаётся группа
5. **Время ответа** — "Петя: только после 8" → агент учитывает при координации

### 2.3. Анти-спам механизм для получателей

Текущая система уже имеет autonomy rules (`auto_approve` для close friends), но нужно добавить:

1. **Rate limiting по инициатору:** макс. 1 запрос "кто свободен" в 6 часов
2. **Quiet hours:** агент друга автоматически откладывает запрос до утра, если получен ночью
3. **Мягкий отказ агента:** вместо "Отклонено" — "Петя сейчас занят, но обычно свободен по пятницам. Напомнить?"
4. **Прозрачность для получателя:** "Ваш агент автоматически ответил: 'Свободна' на запрос Маши" (уже есть `agent_dialog_auto` event)

## 3. Переосмысление "Найти человека"

### 3.1. Проблемы текущей реализации

1. **LinkedIn-синдром.** NetworkSheet — это форма с categories/urgency/visibility. Пользователи мессенджера НЕ хотят заполнять формы.
2. **Оторвано от переписок.** Needs/Offers живут отдельно от чатов. Пользователь говорит другу "ищу дизайнера" в чате, но это не попадает в matching.
3. **Холодный matching.** Embedding similarity без social proof — это алгоритм, а не рекомендация друга.
4. **Нет контекста "зачем".** "Ищу React-разработчика" — для проекта? На работу? Для хакатона? Для консультации?

### 3.2. Новая концепция: "Умные знакомства через переписки"

#### Слой 1: Пассивное извлечение (Zero-effort)
Агент **сам** замечает потребности и навыки из переписок:

**Обнаружение потребности (Need Detection):**
Пользователь пишет другу: "Не знаю хорошего стоматолога, третий раз меняю..."
→ Агент создаёт implicit need: `{ description: "стоматолог", source: "detected", confidence: 0.8 }`
→ Показывает nudge на экране Relationships: "Заметил, что вы ищете стоматолога. Поискать среди знакомых?"

**Обнаружение навыков (Skill Detection):**
Контакт пишет: "Закончил курсы по фотографии, теперь снимаю свадьбы"
→ Агент обновляет `contact_intelligence` + создаёт implicit offer
→ Когда другой пользователь спросит "кто фотографирует?" — уже есть match

**Критично:** implicit needs/offers НИКОГДА не шарятся без explicit consent. Это ТОЛЬКО подсказки инициатору.

#### Слой 2: Контекстные подсказки (Smart Suggestions)
Когда пользователь набирает сообщение или открывает контекстную панель:

```
┌─────────────────────────────────────┐
│ 💡 Подсказка от агента              │
│                                     │
│ Вы упоминали, что ищете дизайнера.  │
│ Ваш друг Коля занимается дизайном   │
│ (из вашей переписки от 15 марта).   │
│                                     │
│ [Попросить познакомить]  [Не надо]  │
│                                     │
│ Или: Маша знает дизайнера —         │
│ через Петю (2 рукопожатия)          │
│ ⭐⭐⭐⭐ Trust score                  │
│ [Попросить Петю представить]         │
└─────────────────────────────────────┘
```

#### Слой 3: Координация знакомства
Когда пользователь решил "познакомиться":

1. **Агент инициатора** → **Агент посредника** (если через mutual contact):
   "Иван ищет дизайнера для лендинга. Ты знаешь Катю, которая делает дизайн. Можешь представить?"

2. **Агент посредника** → проверяет автономию:
   - Close friend + low-risk request → auto-approve, передаёт агенту Кати
   - Acquaintance → спрашивает посредника

3. **Агент Кати** → получает запрос с контекстом:
   "Друг вашего друга Пети ищет дизайнера для лендинга. Показать ваш контакт?"

4. **Результат:**
   - Approved → создаётся групповой чат "Иван + Катя (знакомство через Петю)"
   - Или → Иван получает контакт Кати с контекстом

#### Слой 4: Упрощённый UI вместо NetworkSheet

Текущий NetworkSheet с формами нужно заменить на **диалоговый интерфейс**:

```
┌──────────────────────────────────────┐
│ 🔍 Найти человека                    │
│                                      │
│ [Кого ищете? напишите своими словами]│
│                                      │
│ "дизайнер для лендинга"              │
│                                      │
│ 🤖 Ищу в вашей сети...              │
│                                      │
│ Прямые контакты:                     │
│ 👤 Коля — дизайн, фриланс           │
│    через вашу переписку              │
│    [Написать]                        │
│                                      │
│ Через друзей:                        │
│ 👤 Катя — UI/UX дизайнер            │
│    через Петю · ⭐⭐⭐⭐              │
│    [Попросить представить]           │
│                                      │
│ В сети:                              │
│ 👤 Анонимный (друг друга)            │
│    веб-дизайн, лендинги             │
│    [Запросить знакомство]            │
└──────────────────────────────────────┘
```

**Ключевое отличие от текущего:** одно текстовое поле вместо формы. AI сам определяет category, urgency, visibility по контексту.

## 4. Новые A2A-сценарии

### 4.1. "Давайте выберем" (Collaborative Decision)

**Суть:** Группа друзей не может выбрать ресторан/фильм/дату встречи. Агенты координируют.

**Механика:**
1. Инициатор: "Выберем ресторан на субботу, 4 человека"
2. Агенты каждого участника:
   - Знают предпочтения (из `contact_memory`: "не ест мясо", "любит японскую кухню")
   - Знают расписание (из контекста переписок)
   - Голосуют от имени пользователя (если auto-approve) или спрашивают
3. Результат: "Пересечение: суши-бар Tanuki, суббота в 19:00. Все могут."

**Данные:** `contact_memory` (preferences), `contact_intelligence.persona.activeTopics`, mood

**Wireframe:**
```
┌──────────────────────────────────────┐
│ 📋 Голосование                       │
│ "Ресторан на субботу"                │
│                                      │
│ Варианты:                            │
│ 🍣 Tanuki — 3/4 голосов             │
│    Маша ✅ Петя ✅ Коля ✅ Аня ⏳    │
│                                      │
│ 🍕 Pizzeria — 2/4 голосов           │
│    Маша ✅ Петя ❌ Коля ✅ Аня ⏳    │
│                                      │
│ 💡 Агент: Аня не ест мясо, Tanuki   │
│    подходит лучше. Ждём её ответа.   │
│                                      │
│ [Добавить вариант] [Завершить]       │
└──────────────────────────────────────┘
```

### 4.2. "Care Chain" (Цепочка заботы)

**Суть:** Агент замечает, что друг грустит (mood: declining, significantChange: true). Предлагает другим друзьям написать ему — но не от лица AI, а как естественную инициативу.

**Механика:**
1. Proactive engine обнаруживает: mood = declining у Маши
2. Агент Маши (с её разрешения!) сигнализирует агентам близких друзей
3. Агент Пети (close friend) получает nudge: "Маша, кажется, переживает. Может, стоит написать?"
4. Петя решает сам. Агент может предложить черновик с учётом контекста

**Критично:** информация о настроении НИКОГДА не раскрывается напрямую. Агент говорит "давно не общались" или "может стоит написать", но не "она грустит".

**Consent flow:**
- Маша должна разрешить в настройках: "Разрешить моему агенту просить друзей о поддержке" (opt-in, по умолчанию OFF)
- Правило autonomy: `dialogType: 'care_chain'`, default: `ask_user`

### 4.3. "Подарочный координатор" (Gift Intelligence)

**Суть:** Приближается ДР друга. Агенты координируют подарок.

**Механика:**
1. `contact_memory` содержит факт `{ category: 'date', fact: 'День рождения 15 апреля' }`
2. За 2 недели до даты → proactive trigger: `birthday_upcoming`
3. Агент инициирует care chain среди close friends:
   - Собирает идеи подарков (`/gift-ideas` endpoint уже существует!)
   - Предлагает скинуться
   - Координирует: "Петя дарит книгу, Аня — торт. Хотите добавить?"

**Wireframe:**
```
┌──────────────────────────────────────┐
│ 🎁 ДР: Маша, 15 апреля             │
│ через 12 дней                        │
│                                      │
│ Что мы знаем:                        │
│ · Любит японскую кухню               │
│ · Недавно начала рисовать            │
│ · Хотела набор акварели (из чата)    │
│                                      │
│ Координация:                         │
│ Петя → книга по акварели ✅          │
│ Аня → сертификат на суши 🔄         │
│ Вы → ?                               │
│                                      │
│ 💡 Идеи: набор акварели Winsor&Newton│
│    (~3000р), мастер-класс (~5000р)   │
│                                      │
│ [Я дарю это]  [Скинемся]  [Пропущу] │
└──────────────────────────────────────┘
```

### 4.4. "Эксперт рядом" (Knowledge Routing)

**Суть:** Пользователь задаёт вопрос → агент знает, что кто-то из знакомых — эксперт.

**Механика:**
1. Пользователь пишет в любой чат: "Кто-нибудь разбирается в налогах для ИП?"
2. Агент детектирует вопрос-запрос из переписки
3. Проверяет `contact_intelligence` + `contact_memory`:
   - Петя — бухгалтер (из memory: `{ category: 'work', fact: 'работает бухгалтером' }`)
   - Коля — сам ИП (из memory: `{ category: 'work', fact: 'открыл ИП в 2025' }`)
4. Nudge: "Петя — бухгалтер, может помочь с налогами. Спросить?"

**Отличие от "Найти человека":** здесь речь о quick question, не о длительном сотрудничестве. Один вопрос — один ответ.

### 4.5. "Собери группу" (Group Formation)

**Суть:** Создание группы под активность с AI-помощью.

**Механика:**
1. Пользователь: "Хочу собрать команду на хакатон, нужен дизайнер и бэкендер"
2. Агент ищет среди контактов:
   - Дизайнеры: Катя (через `contact_intelligence`), Аноним через Петю
   - Бэкендеры: Коля (из переписки "пишу на Go")
3. Создаётся план-приглашение
4. После подтверждений → создаётся группа с участниками

**Quick Wins (Low Effort + High Impact):**
- UI экрана результатов "Кто свободен?" — backend уже стримит данные
- Замена формы на текстовое поле — NLP-парсинг одного предложения

**Strategic Bets (High Effort + High Impact):**
- Пассивное извлечение потребностей из переписок
- Smart targeting (кого звать на основе контекста)

**Money Pit (High Effort + Low Impact):**
- Визуализация социального графа
- Полная координация подарков

## 7. MVP Scope (1-2 недели)

### Неделя 1: Результаты "Кто свободен?" + Упрощённый поиск

**Backend (уже почти готово):**
- WebSocket `partialResult` уже стримится → нужен только frontend
- Добавить: NLP-парсинг intent из одного предложения (1 LLM call, classification model)
- Добавить: endpoint "создать группу из ответивших"

**Frontend:**
1. **WhosFreeResultsScreen** — новый компонент:
   - Открывается после запроса "Давай соберёмся"
   - Карточки друзей стримятся в реальном времени (слушает `agent_dialog_update` с `partialResult`)
   - Каждая карточка: аватар, имя, статус (свободен/занят/ждём), метка автономии, сообщение
   - Кнопка "Создать группу" (активна когда >= 2 ответили "свободен")
   - AI-саммари внизу ("2 из 4 свободны, Маша после 8")

2. **Замена input "Кто свободен?":**
   - Текущий: текстовое поле + кнопка (уже есть в Relationships.tsx)
   - Новый: полноэкранный bottom sheet с:
     - Большое текстовое поле "Что хотите?"
     - Под полем: AI-чипы-подсказки ("Сегодня вечером", "В эти выходные", "Помощь нужна")
     - Предпросмотр: "Спросим 5 друзей" (на основе smart targeting)

3. **Замена NetworkSheet формы:**
   - Одно текстовое поле "Кого ищете?"
   - Результаты: 3 секции (Прямые контакты / Через друзей / В сети)
   - Кнопки действий на каждом результате

### Неделя 2: Smart Targeting + Nudge-интеграция

**Backend:**
- Smart targeting: функция `selectBestFriends(userId, intent)` — фильтрует друзей по релевантности
- Nudge для detected needs: добавить trigger `detected_need` в proactive engine (уже есть в UI: `triggerIcon('detected_need')`)
- Rate limiting: макс. 1 запрос "кто свободен" в 6 часов на пользователя

**Frontend:**
- В карточках результатов: AI-обогащение ("давно не общались", "обычно свободна вечером")
- Nudge "detected_need" ведёт в упрощённый поиск

### Что НЕ входит в MVP:
- Голосования/выбор ресторана
- Care chains
- Координация подарков
- Визуализация графа
- Пассивное извлечение навыков из переписок (только needs)

## 8. Anti-patterns и Принципы

### Чего ТОЧНО НЕ делать

| Anti-pattern | Почему опасно | Альтернатива |
|---|---|---|
| **Рассказывать о настроении друга** | "Маша грустит" — это предательство доверия | "Может, стоит написать Маше — давно не общались" |
| **Auto-share skills/needs без consent** | "Ваш друг ищет дизайнера, я отправил ваш контакт" — нарушение приватности | Всегда спрашивать обе стороны |
| **Broadcast всем друзьям** | 15 друзей получают "ты свободен?" — это спам | Smart targeting: 3-5 самых релевантных |
| **Создавать потребности за пользователя** | Агент решил "вам нужен стоматолог" — creepy | Только подсказка: "Заметил, что вы упоминали... Поискать?" |
| **Показывать, что агент "читает переписки"** | "Из вашей переписки с Петей от 15:34..." — creepy | "На основе ваших разговоров" — без точных цитат |
| **Auto-approve для acquaintances** | Знакомый получает доступ к данным без спроса | `ask_user` по умолчанию, `auto_approve` только для close |
| **Навязывать follow-up** | "Вы не создали группу после опроса. Создать?" × 3 раза | Один nudge, без повторов |

### Принципы проектирования

1. **Человек решает, агент координирует.** Агент никогда не действует от имени пользователя без разрешения. Он предлагает, а пользователь подтверждает.

2. **Прозрачность автономии.** Если агент действовал автоматически — пользователь ВСЕГДА видит что именно было сделано и может отменить.

3. **Gradual disclosure.** Не показываем "мы проанализировали 200 сообщений". Показываем только actionable insight.

4. **Social proof > Algorithm.** "Через Петю" важнее чем "87% match". Люди доверяют людям.

5. **Minimal friction.** Одно текстовое поле > форма с 5 dropdowns. AI парсит контекст.

6. **Fail gracefully.** Если AI не может определить intent → fallback к простому broadcast. Если matching пуст → "Не нашёл среди знакомых. Попробуйте расширить видимость."

7. **Respect temporal context.** Не тревожить ночью. Учитывать часовые пояса. Учитывать "занят на работе".

## 9. Вопросы для дизайнера

1. **Экран результатов "Кто свободен?"** — как показать стриминг ответов? Анимация появления карточек? Скелетоны? Live-counter "ответили 2 из 5"?

2. **Карточка друга в результатах** — как визуально отличить "ответил сам" от "ответил агент"? Иконка бота? Цвет? Подпись?

3. **Степень детализации "умного таргетинга"** — показывать ли пользователю ПОЧЕМУ мы выбрали этих 4 друзей из 15? Или это over-information?

4. **Переход от результатов к действию** — как выглядит "Создать группу"? Автоматически добавить всех ответивших? Дать выбрать? Предложить название?

5. **Bottom sheet vs Full screen** — для "Давай соберёмся" лучше bottom sheet (как сейчас NetworkSheet) или полноэкранный flow? Учитывая что результаты стримятся 1-2 часа.

6. **Nudge о detected need** — как выглядит? Встроенный в список контактов? Отдельная карточка? Toast-notification?

7. **Trust score визуализация** — звёзды (как сейчас в NetworkSheet) или другой формат? "Через 1 рукопожатие" vs числовой score?

8. **Empty states** — что показывать если: 0 друзей свободны? 0 matches по запросу? Все отказали?

9. **Состояние ожидания** — запрос "кто свободен?" может длиться часы. Как показать активный запрос? Badge? Floating widget? Push-notification когда ответят все?

10. **Mobile keyboard** — при вводе "Что хотите?" клавиатура съедает половину экрана. Как показать подсказки-чипы так, чтобы они были видны?

## 10. Вопросы для Tech Researcher

1. **NLP-парсинг intent из одного предложения.** Можно ли gpt-4o-mini (classification task, temp 0.1) надёжно парсить `{ type, time, groupSize, mood }` из "хочу в бар вечером"? Или нужен fine-tuned classifier? Latency budget: <500ms.

2. **Smart targeting scoring formula.** Как взвешивать факторы (relationship_level, mood, silence_days, topic_relevance, denial_history)? Нужна ли ML-модель или хватит rule-based weighted sum?

3. **Implicit need detection из переписок.** Текущий proactive engine уже сканирует каждые 15 минут. Можно ли добавить need-detection как ещё один trigger без значительного роста LLM-затрат? Evaluation: precision vs recall trade-off.

4. **Embedding-based matching quality.** Текущий `generateEmbedding()` (server/ai/embeddings.ts) — какая модель? Достаточна ли для семантического matching "нужен стоматолог" ↔ "работаю зубным врачом"? Нужен ли re-ranking step?

5. **WebSocket scalability.** Текущий `sendToUser()` — per-user connections. При "кто свободен?" генерируется N WebSocket events (по одному на друга). При 50 друзьях — 50+ events. Нужен ли batching? Throttling?

6. **Privacy of detected needs.** Если агент детектирует "ищу стоматолога" из переписки — это PII? Хранить ли detected needs отдельно от explicit? Нужна ли дополнительная шифрация?

7. **A2A dialog scalability.** Таблица `agent_dialogs` может расти быстро (1 запрос "кто свободен?" = N child dialogs). Нужна ли архивация / TTL? Текущий `checkExpiredDialogs()` уже есть, но только по `expiresAt`.

8. **Offline agents.** Что если друг не онлайн? Текущая система: WebSocket `agent_dialog_request` не доставляется offline users. Нужна ли очередь? Push-notifications?

9. **Multi-hop matching.** Текущий `getSocialDistance()` считает до 2 hops. Для "найти человека" нужно ли расширять до 3? Какова цена в latency и trust degradation?

10. **Consent state machine.** Текущие статусы: `pending → auto_approved | approved | denied | expired | cancelled`. Достаточно ли для care chains и gift coordination, где нужен `partial_approved` (одобрил участие, но не сумму)?
